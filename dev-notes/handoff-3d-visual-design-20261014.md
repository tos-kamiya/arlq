## 目的と現在の段階

ARLQのゲームルールを全く変えず、GUIの見た目を強化するための検討をまとめる。
ユーザーは実装に移らず検討だけ行うよう指定しており、現時点では描画コードの変更や素材作成は行っていない。
本資料の作成は、検討内容を引き継ぐためのドキュメント化である。

## ユーザーが指定した条件

- ゲームルールは全く変えない。
- 素材はドット絵にせず、透明感のある3D表現を検討する。
- 見下ろし型のビューを維持する。
- FOVや可視化範囲はリアルな照明表現に寄せず、現在のように色が変わる表現でよい。
- 音は当面、検討・実装の対象外とする。
- TUI・GUIが共有するゲーム進行エンジンを、3D版でも共有できる構成を検討する。

実際の3Dモデルを描画するか、3Dモデルから作った2D画像を描画するかは未決定。

## 提案した見た目の方向性

「ガラス製の立体盤面に、現在の視界表示を重ねる」画面を提案した。
これは検討案であり、具体的な造形や配色が承認されたわけではない。

| 対象 | 検討案 |
| --- | --- |
| カメラ | 真上に近い固定の見下ろし。平行投影でマスの位置関係を保つ |
| 床 | 薄いガラス板のようなタイル。控えめな厚み、反射、陰影 |
| 壁 | 低い半透明ブロック。上面と縁で形を示し、駒を隠しにくくする |
| プレイヤー・敵 | 透明な樹脂や水晶を思わせる立体駒。輪郭は明確にする |
| 記号 | 駒の上面などに既存の識別文字や強化記号を残す案 |
| 階段・宝・障害物 | マス内に収まる立体物 |
| UI | 半透明パネルに鮮明な文字、LPバー、進行状況などを配置 |

透明感は単に透明度を上げるだけでなく、淡い色、縁の光、柔らかい陰影で表現する。
反射や発光で、盤面の記号やFOVの色が読みにくくならないようにする。

## FOVと可視化範囲

視界の判定は共通エンジンに任せ、描画側は渡された範囲を表示する。

- 現在の視界・探索済み・未探索という既存の区分を維持する。
- 区分はタイルの色や明るさの切り替えで示す。
- 視界境界や移動範囲の表示は、立体素材の上でも読み取れる色や線で表す。
- リアルな光源、影、遮蔽によって新たな視界判定を行わない。
- 色や線の具体的なデザインは未決定。

素材用の陰影と、ゲーム上の視界表示は役割を分ける。
装飾の陰影が、実際の視界範囲と誤認されない表現にする。

## 共通エンジンとの構成

3D版は、共通エンジンを使う第三の描画フロントエンドとして構成できる見込み。

```text
共通のゲーム進行エンジン
  ├─ TUI：文字で描画
  ├─ GUI：図形と文字で描画
  └─ 3D ：立体タイルと駒で描画
```

### 現在のコードで確認できた接点

- `src/arlq/game_engine.py`: ゲーム進行と、UIへの描画情報の受け渡し。
- `src/arlq/pyglet_funcs.py`: 現在のGUI描画と入力処理。`draw_stage()` が盤面、プレイヤー、敵、現在の視界、探索済み範囲などを受け取る。
- `src/arlq/display.py`: 両フロントエンドで使う文字・表示判断。敵の識別状態、擬態、表示色、強化記号などを扱う。
- `src/arlq/blessed_funcs.py`: TUIの描画と入力処理。
- `src/arlq/defs.py`: ゲーム定数、エンティティ、種族・出現定義。

### 責務の分担案

| 共通エンジン・既存の表示判断 | 3Dフロントエンド |
| --- | --- |
| 移動、戦闘、ターン、乱数、FOV判定 | モデル、材質、カメラ、描画 |
| どの情報を表示してよいかの判断 | 表示可能な情報を立体表現へ変換 |
| 既存の操作に対するゲーム進行 | キー入力などを既存の操作へ変換 |

`display.py` の表示判断を利用し、記号・色・識別状態に対応するモデルや材質を選ぶ案が考えられる。
現在の文字向けの出力だけで十分か、最小限の共通化が必要かは実装前に確認する。
3D側がエンティティの実際の種類だけを見てモデルを選ぶと、未識別情報が漏れるため注意する。

実装場所やUIとの接続には調整が必要になる可能性があるが、3D専用にゲームルールを作り直す必要はない。
既存の小さな構成を維持し、大きな抽象化や不要な依存追加は避ける。

## ルールと情報を変えないための条件

- 未識別の敵は種類が分からない共通の姿にする。
- 宝に擬態している敵は、既存の表示条件に従って宝と同じ姿にする。
- 半透明の壁越しにも、表示対象でない敵や未探索の床は描画しない。
- 装飾用の光や影から、隠れた地形・敵の存在が分からないようにする。
- 既存の色、記号、薄表示などが伝えている情報を失わない。
- 描画更新とターン進行を分ける。描画フレーム数やアニメーション終了でターンを進めない。
- 演出によってキーリピートや入力受付の条件を変えない。
- 装飾や素材の変化にゲーム用の乱数を使わず、ゲームの生成結果に影響させない。
- TUIと既存GUIの動作を維持する。

## 描画方式の候補

| 方式 | 特徴 | 検討上の課題 |
| --- | --- | --- |
| 3Dモデルから作った2D画像 | 固定視点なら立体的な質感を表現でき、既存GUIへの影響を抑えやすい | 視点・光・素材の変化は画像に依存する。実際の3D描画とは異なる |
| 実際の3Dモデルを描画 | 光や反射を動かせる | モデル描画、半透明物の重なり、描画順、描画ループの対応が必要 |

会話では、改修範囲との釣り合いから固定視点の3D風素材を先に検討する案をおすすめした。
ユーザーは方式を選択していないため、このおすすめを確定事項として扱わない。
既存Pygletを継続するか、別の描画技術を使うかも未決定。

現在のGUIは画面更新時に描画物を作り直す方式になっている。
常時動く光や大量の粒子などを追加する場合は、GUI側の描画方法の調整が必要になる。

## 次の検討事項

1. 実際の3D描画を必要とするか、固定視点の3D風画像で目的を満たせるか。
2. 真上からの角度、壁の高さ、透明感の強さ。
3. 識別文字を残す位置と、未識別・擬態・強化状態などの表現。
4. 現在のマス配置と画面全体の情報量を維持できる素材サイズ。
5. 共通エンジンと3D側の描画・入力ループの接続方法。
6. 素材の制作方法、配布サイズ、対応環境と描画負荷。

ユーザーから実装指示があるまでは、検討の範囲に留める。

## 実装に進む場合の検証方針

同じ初期条件と操作列で、TUI・既存GUI・3D版のゲーム状態が一致することを確認する。
既存のヘッドレステストに加え、必要に応じてゲームプレイトレースを比較する。
入力変換、キーリピート、視界表示、未識別情報の保護はフロントエンド側でも確認する。

共通エンジンなどを変更する場合は、リポジトリの指示に従い `uv run -p .venv/bin/python pytest` を実行する。
3Dの透明度、重なり、文字の読みやすさ、動作の滑らかさは実際の画面で検証する。

この検討ではGUIの実機確認、3Dの試作、性能検証は行っていない。
