# 静的バランス調整スクリプトの実装ハンドオフ

作成日: 2026-09-06

## 目的と作業範囲

開発時に自動プレイを多数実行し、モンスターの食料回復量・出現数・出現確率の候補を評価する。採用した設定はゲーム全体で固定する。プレイ中の動的難易度調整は対象外。

ユーザーが求めているのは、適切な難易度に加え、「出現したモンスターを出現した順に倒すことが最適解にならない」バランスである。倒せる敵を温存したり、別の敵を先に倒したりする判断に価値を持たせたい。

この資料は実装の引き継ぎ用であり、スクリプトの実装・探索の実行・ゲーム定数の変更はまだ行っていない。以下の数値やCLIは提案であり、既存の機能やユーザーが承認した目標値ではない。

## 合意事項と設計上の仮定

- 静的な食料・出現設定を自動探索する。
- 単に遭遇順に倒すより、状況に応じて順序を選ぶ価値を評価する。
- モンスターごとの討伐率や選択率を一律に揃えることを目的にしない。
- 最終出力は比較可能な複数候補と根拠とし、ゲームの定数を自動で書き換えない。
- 「出現順」は、前の提案ではプレイヤーが発見した順と解釈している。これはユーザーによる明示的な定義ではないため、レポートに定義を明記する。内部の生成順とは区別する。
- 目標クリア率、許容する序盤死亡率、必要な方針間の差は未確定。設定可能にし、未指定なら現状測定と候補比較まで行い、「最適」と断定しない。

## 現状のコードと再利用箇所

| 場所 | 現状 | 実装時の扱い |
| --- | --- | --- |
| [defs.py](../src/arlq/defs.py) | 種族ごとの `feed`、強さ、ステージ別 `SpawnConfig`、LP上限・初期値、再出現間隔 | ゲーム定数はここに維持。候補を評価中だけ適用し、必ず元に戻す |
| [arlq.py](../src/arlq/arlq.py) | `spawn_entities`、`respawn_entity`、`update_entities`、ゲームループ | 戦闘・食料・移動のルールを再実装せず再利用 |
| [solver.py](../src/arlq/solver.py) | `build_simulation`、`step_simulation`、`simulate_game`、固定戦略 | 方針差し替えとイベント計測の基盤。現行方針も比較対象として残す |
| [branch_analyzer.py](../src/arlq/branch_analyzer.py) | ビーム探索、状態複製・経路探索、勝利履歴の再生 | 上位候補の勝ち筋と局所的な順序差を確認する補助 |
| [balance_search.py](../src/arlq/balance_search.py) | `BalanceTuning`、`patched_tuning`、近傍生成、プロセス並列評価 | 候補適用と探索の骨格を活用。新目的を旧評価と混同しない |
| [utils.py](../src/arlq/utils.py) | 独自乱数 `MyRandom` と共有インスタンス `rand` | 再現性と状態分岐の際に現在の乱数状態も保存・復元 |
| [developer.md](developer.md) | 現行ソルバ・分岐解析・探索の使用方法 | 実装後に新しい評価方法と実在するコマンドを追記 |

現行探索は、ステージ1では `a A b c d` の出現数と `b` の食料、ステージ2では `a A b c C d` の出現数を調整する。勝利履歴における選択優先度の分散を最小化する山登り探索であり、今回の評価目的とは異なる。

### ルール上の注意

- `SpawnConfig.population` は整数なら配置数、小数ならその確率で1体を配置する。`1` と `1.0` の型も保持する。確率は現行実装では100段階の乱数で判定される。
- 現在のモンスター初期配置は整数。同行者には `0.7` が指定されている。確率を個体数分布や再出現率と混同しない。
- 食料の種族定義は両ステージで共有される。食料変更は必ず両ステージで検証する。
- 討伐後のLPは `max(1, min(LP_MAX, lp + feed))`。呪われた剣のLP減少はその後に適用される。名目食料と実際の回復量を別々に記録する。
- 討伐すると装備は相手の `item` で上書きされる。装備を持たない敵を倒しても現在の剣・毒が消える。毒の解除方法を剣の獲得だけに限定して評価しない。
- 討伐後の再出現キューがある。初期配置数だけから全プレイ中の食料総量を推定しない。
- 戦闘敗北では再配置とLP下限補正がある。これを利用する方針が候補を有利にしていないか記録し、許容するかは別の設計判断とする。

## 評価方針

### 1. 同じ情報条件の方針を比較する

主要比較はプレイヤーが知り得る視界・地形・識別情報を使う。既存ソルバは完全情報なので、そのまま人間向け評価とは呼ばない。最初に完全情報で評価の配線を確認してもよいが、結果には `full-information` と明記する。

最低限、次の方針を用意する。

| 方針 | 行動 | 役割 |
| --- | --- | --- |
| 発見順 | 既知で到達可能な敵を初発見順に選ぶ。既知の倒せない敵は保留 | 単純な討伐順の基準 |
| 近距離優先 | 同じ情報条件で近い候補を選ぶ | 発見順方針の往復移動だけが差の原因になることを検出 |
| 状況判断 | LP、距離、育成、装備更新を考慮して倒す・温存する | 順序選択の価値の測定 |
| 食料優先・育成優先 | 優先軸を変えた少数の方針 | 一つの固定攻略法への過適合を検出 |

未知の `?` から実際の種族・強さ・食料を参照しない。未知敵への接触規則、未探索地点の選び方、同行者・宝箱の扱い、同順位の決定方法は比較方針間で共通にする。探索・経路計画の差で討伐順の効果を水増ししない。

発見順は個体ごとの初観測時刻を記録する。同時発見は安定した規則で並べ、再出現は新個体として扱う。未識別でも観測した事実は記録する。生成順や内部リスト添字を発見順の代用にしない。

現行 `choose_target` は隣接した候補を先に選び、`choose_move_direction` は計画済み目標を保持する。状況判断方針では、隣接しても温存できること、LP・装備の変化後に目標を再検討できることを確認する。

### 2. ゲーム全体の指標

- 方針別・ステージ別のクリア率：1シード・1方針のプレイを1標本とする。
- 序盤の餓死率：序盤のターン境界を設定値として保存する。
- クリア時の歩数・残LPの中央値と分位点：勝利したプレイを分母とし、全終了時平均と区別する。
- 終了理由：勝利、LP切れ、行動停滞、ターン上限、実行エラーを区別する。エラーを通常敗北として隠さない。
- 種族ごとの討伐数、初討伐時刻、食料の実効回復量と上限による無駄、装備遷移、戦闘敗北回数。
- レアや特定装備を使わない勝ち筋の有無。禁止実験を使う場合、通常条件のクリア率と別に表示する。

同じシード集合について `Δclear = 状況判断のクリア率 − 発見順のクリア率` を計算し、近距離優先との比較も併記する。区間推定はシード単位の対応付き再標本化などで行い、方針の乱数反復がある場合もシード単位にまとめる。複数ステージの値を一つの平均だけで隠さない。

現行分岐解析の `wins / leaves` は探索終端中の勝利割合であり、プレイのクリア率ではない。ビーム幅等にも依存するので、主要指標に使わない。探索で勝利未発見でもクリア不可能とは断定しない。

### 3. 「見送る価値」を局面単位で確認する

全体クリア率差だけでは、別の固定順序が強いだけという可能性が残る。上位候補について、勝敗を問わずサンプルした局面で次を行う。

1. 既知かつ倒せる敵があり、別の行動も取れる局面を抽出する。
2. 状態と現在の乱数状態を複製し、「その敵へ向かって倒す」と「別の目標を先に選ぶ」を分岐する。移動・途中接触・食料消費も通常ルールで進める。
3. 分岐後は同じ継続方針・予算で評価し、勝敗とコストの差を記録する。探索打ち切りや区別不能は未判定とする。
4. 見送る側が有利な割合を、有効な比較局面を分母として出す。標本数と未判定数も示す。
5. 同じ種族で「今倒す」が有利な例と「後回し」が有利な例を、LP・装備・距離とともに出力する。

単に討伐順が発見順と違う割合は補助指標に留める。勝利経路だけを収集すると偏るため、局面収集を勝利条件で絞らない。完全情報の探索を使った局面診断は、人間相当の方針比較と別欄にする。

## 探索対象と制約

初期版は基本モンスターの食料と整数の出現数に絞り、既存ルール内で効果を確認する。設定形式は出現数と確率を明示的に区別できるようにする。レア等の確率探索は次段階で有効化し、現行の0.01刻みの意味を保つ。

- 食料は種族ごと、配置はステージごとに設定する。全種の値を一括で同じ倍率にしない。
- 各パラメータの上下限・刻み幅、総配置数上限を探索設定に持たせる。
- ボスと宝箱の成立条件は固定。初期版では強さ、剣倍率、LP上限、再出現間隔、地形を固定する。
- 種族の意図を壊す値を許可しない。食料を持たない敵や吸収効果のある敵を、無条件で通常食料源に変更しない。
- 配置処理が過密盤面で停止しないよう、候補の上限検証と実行時間上限を用意する。
- 現在値からの変更量を記録し、同程度の成績なら変更の小さい候補を優先する。

## 探索と検証の流れ

1. 現行値で全方針の基準値と1プレイの評価時間を測定する。
2. 制約内のランダム候補を複数作り、現行値も必ず含める。
3. 共通の探索用シードで粗く評価し、有望な複数候補を残す。
4. 各候補の周囲を局所探索する。食料と出現数を同時に変更する候補も含める。
5. 独立した検証用シードで絞り込み、上位候補に局面診断を行う。
6. 最後に未使用の最終評価用シードで評価し、複数候補をレポートする。最終結果を見て再調整する場合は、その集合を検証用へ移し、新しい最終集合を用意する。

最初の規模の目安は粗評価100シード、最終評価1,000シード程度。ただし固定の必須値ではなく、実測時間と差の不確かさに応じて変更する。方針・ステージ数を含む総プレイ数、候補数、時間予算を表示する。

既存の開発資料には勝利シードだけを渡す例があるが、今回の難易度評価では使用しない。勝敗で選別していないシードを使う。同じシードでも配置数変更で乱数消費が変わり、配置の完全対応は保証されない。その制約を明記する。

候補選定はまず目標難易度・序盤死亡率等の条件を満たすか判定し、その中で順序選択の価値と変更量を比較する。クリア率差の最大化だけを目的にしない。条件未指定なら指標間のトレードオフを示す候補一覧にする。条件を満たす候補がなければ、その事実と不適合理由を出す。

## 実装構成・再現性

小規模な既存構成を保ち、汎用フレームワークや新しい重い依存は導入しない。新評価を既存探索の明示的なモードとして追加するか、薄い別CLIを設けるかは実装時に決めてよい。旧指標・旧CLIの意味を黙って変更しない。

- シミュレーションは方針決定とゲーム進行を分け、GUI/cursesと同じゲームルールを使う。複数箇所にあるターン進行の順序の一致を先に確認する。
- 候補適用は `try/finally` 相当で全変更を復元する。例外発生後やワーカープロセス再利用時にも設定が漏れないようにする。
- 共有定数と `rand` があるため、評価の並列化はプロセス単位を基本とする。スレッドで異なる候補を同時適用しない。
- 探索候補生成・方針の乱数はゲーム用 `rand` と分離する。分岐には初期シードだけでなく現在の乱数状態を保存する。
- キャッシュキーに候補全体、シード、ステージ、方針版、情報条件、実行フラグ、予算、コード版を含める。
- 同じ設定でワーカー数を変えても結果と候補順位を再現できるよう、集約・同点処理を安定させる。
- 中断時にも完了分を保存し、再開時は設定の一致を確認する。

## 入出力の提案

未実装のインターフェース案として、設定ファイル、出力先、探索乱数シード、各評価用シード集合、ワーカー数、候補数・時間予算、再開指定を受け付ける。

設定にはパラメータ範囲、対象ステージ・ゲームオプション、方針と情報条件、目標範囲、序盤の定義、プレイ打ち切り条件を含める。標準ライブラリで扱えるJSON等でよい。

出力例の構成:

- `manifest.json`: コード版、未コミット変更の有無、実効設定、全シード、乱数仕様、方針版、実行時間。
- `candidates.jsonl`: 候補ID、全パラメータ、集約指標、区間推定、制約違反。
- `runs.jsonl`: 候補・シード・ステージ・方針ごとの結果と終了理由。
- `decision_examples.jsonl`: 順序選択が結果を変えた局面、観測情報、両分岐の結果、再生に必要な履歴。
- `report.md`: 現行値と上位候補の比較、採用理由、トレードオフ、未検証事項。

候補の値は提案として出力するだけとし、`defs.py` を自動編集しない。レポートに、有限の方針・シード・探索予算による評価であり最適性の証明ではないことを記す。

## 実装順と受け入れ条件

### 段階1: 測定基盤

- 既存ソルバの基準値を保存し、方針差し替え後も既存方針で同じ結果になる。
- 通常ゲームとシミュレーションの食料・装備更新・再出現・ターン消費が一致する。
- 終了理由、実効回復量、発見順・討伐順を記録できる。
- 候補適用後の復元、型保持、乱数再現性を対象を絞って検証する。

### 段階2: 方針比較

- 発見順、近距離優先、状況判断を同じ情報条件で比較できる。
- 未観測の地形・未識別の種族を方針が参照しないことを確認する。
- 倒せない敵の回避とは別に、倒せる敵の温存が可能である。
- LP上限による食料温存、装備上書き、再出現個体の発見順を小さな局面で確認する。

### 段階3: 静的探索

- 複数パラメータ候補を探索し、共有食料の変更を両ステージで評価する。
- 探索・検証・最終評価シードの混入がない。
- 同じ入力で再現でき、ワーカー数変更・中断再開でも結果が一致する。
- 制約を満たさない候補しかない場合も、適切な理由を出力する。

### 段階4: 順序選択の検証と引き渡し

- 方針間のクリア率差、近距離優先との差、不確かさを出力する。
- 同じ種族を今倒す／後回しにする価値が変わる具体例を出力できる。見つからなければ未達と報告する。
- 勝ち筋未発見とクリア不可能、打ち切りと死亡を区別する。
- 現行値を含む比較資料を生成し、自動でゲーム定数を変更しない。

実装時の基本チェックは `uv run -p .venv/bin/python python -m compileall src` と `uv run -p .venv/bin/python python -c "import arlq"`。加えて少数シードで両ステージを実行し、上記の再現性・ルール一致を検証する。共有ゲーム進行を変更した場合は可能な範囲でGUI/cursesも確認し、未実施なら明記する。

実装後は開発資料に使い方を追記する。プレイヤー向けルールや採用定数を後で変更する際は、英語・日本語READMEの記述への影響を確認する。
